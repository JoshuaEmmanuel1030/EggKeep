## Overview

Phase 2 makes the delivery detail on `/deliveries` the one place where office admin (Dila, Yani) types a faktur's return lines and the warehouse sorting result, and makes that entry the stock return. Per PO line: the quantity sent back in the line's own unit, a reason, the Osave return number, a note; then the count of broken eggs, with OK as the remainder, saved through the existing `record_return` RPC so stock, the Activities feed and the log show the same numbers. October's sheet rows are imported once, the CSV export keeps the sheet's layout, billing status waits for Phase 3 and PO intake is a separate brainstorm.

Why it matters: returns stopped reaching EggKeep stock on 14 Oct. Since then the sheet has logged about 21,000 "Butir OK" eggs that never re-entered stock, and 3,549 broken Osave eggs are unbilled. Phase 1 (live since 30 Oct) digitised the two columns that carry no information, so nobody switched: one test row in production.

Brainstorm verdict, all six lenses: the place (the faktur detail), the typist (admin), the line table (justified: 13 of 108 return rows have no physical return, and the warehouse count lags the faktur by up to two days) and "stock through `record_return` only" survive scrutiny. Four parts of the hypothesis do not survive as written: (1) a silent "OK = remainder" prefill in front of an irreversible stock write, with no way to undo a return anywhere in the system; (2) `delivery_line_id` as the mechanism that makes stock, feed and log agree, which it cannot do while phones run old bundles; (3) the October import of warehouse counts through `record_return`, which the project's own full spec ruled out and which has five known failure modes on the sheet's real rows; (4) the claim that the export already matches the sheet (it has 22 columns and 8 different headers; the sheet has 21). Each is fixable in the brief with a small rule; none is fixable after launch without SQL surgery.

### Glossary (terms the concept uses without defining; comprehension M8)

- **Faktur / No. Faktur**: the invoice number admin also types into Peachtree; the only business key of a PO in EggKeep. **Faktur balik**: the signed invoice the driver brings back from the store.
- **PO**: a buyer order recorded at loading; recording it deducts stock. There is no PO table; the `purchase_orders` view regroups `activity_logs` rows.
- **Paraf**: initials / sign-off. **PIC**: the admin who typed the row. **Catatan Kondisi**: Novi's tick that the sorting happened.
- **Pecah**: the warehouse's word for broken eggs. **Retak / retakan**: the app's "cracked but sellable" disposition (child item "<PRODUCT> (RETAKAN)"). **Hancur / writeoff**: gone, no stock. **OK / restock**: back into the original FIFO batches. Feed letters O / R / H.
- **Kurang**: the store received fewer than the faktur says; nothing comes back. **Ditolak**: rejected at the DC. **Tukar guling**: swap; goods come back and a replacement goes out as a new PO. **Revisi PO / Masih ditanyakan / Cancel**: paper-only reasons with no physical return.
- **Aryo / No. Retur ARYO / No. Retur OSV**: Osave issues a return number for broken eggs; Aryo is the person who compensates JS for them. Same field, four names today.
- **TST**: Tirta Soeper Telor, the group's own site; returned goods sometimes land there before the warehouse.
- **Shared-egg rows**: two pack SKUs on one order that draw from one egg product, so they share one return cap. **Outbox**: the offline queue that replays a failed write on reconnect.

### Blockers

**B1. A return cannot be undone, and Phase 2 moves 100+ typed numbers a month onto that pipeline.** (structural F1; comprehension B1; codebase 5; design F1; zoom-out F10; implementation F1)
`returns` has a select-only policy (`supabase\migrations\20260904000000_returns.sql` lines 38–42), `return_restocks` references it without cascade, `record_return` is insert-only and skips a line whose id already exists (`20261008000000_returns_sku_code.sql` lines 59–61), and no `void_return` exists anywhere in the repo. `correct_order` refuses once a return exists (`HAS_RETURNS`, `20261021020000_correct_order_guards.sql` lines 97–102). The only person who has ever used the pipeline is the owner, in one careful sitting (136 rows, 13–14 Oct). Admin typing 108 return rows a month will mistype in the first week, and a wrong save (1720 for 172) is a permanent stock delta only SQL can fix, while the store-side half of the same line stays editable forever.
Requirement: the brief names the correction path before anything is built. Minimum: the warehouse save is an explicit button (never on blur; Phase 1's `DeliveryDetail.tsx` saves on blur at lines 32–35, 281, 293), preceded by a confirmation that shows the arithmetic in words, and once returns exist for a line its quantity, SKU and reason lock in the UI with a "hubungi admin" note and an owner SQL runbook. Recommended: a `void_return(p_return_id, p_reason)` RPC that reverses `return_restocks` oldest-first with `void_outflow`'s lock order and voids the retakan inflow it created. Left for the owner (see Key Decisions).

**B2. The October import of warehouse counts is an irreversible bulk stock mutation with five known failure modes.** (implementation F1, F3, F4, F5; design F1; codebase 8, 9, 10; structural F8; zoom-out F3; comprehension M7)
Facts from the sheet and the database: the owner's back-entry already covers 30 Sep–14 Oct and the sheet starts 12 Oct, so 12–14 Oct fakturs would be recorded twice (the cap rejects only when the sum exceeds sold; a partial double passes silently). "Butir OK" is blank on 43 of 108 return rows (e.g. 2610421 N 30, 6 boxes, pecah 300, OK blank), so an "OK = remainder" rule would restock about 600 eggs per such row that nobody counted. Row 2610448 NO10 "55" is packs, not boxes (409 + 141 = 550 = 55 × 10); as boxes it is 9,900 eggs. 41 POs in October were voided (`OUTFLOW_VOIDED`) and the two test POs `TEST-Complete` / `TEST2` exist in production. Restocking ~21,000 eggs into two-to-three-week-old FIFO batches lands on top of physical counts (23–31 Oct) that already show system stock above counted stock. Mapping "Butir Pecah" to `retakan` mints thousands of pieces of RETAKAN stock. `record_return` requires `auth.uid()` (`AUTH_REQUIRED`, lines 38–40), so a service-role script cannot call it. The full spec's Phase 4 (`docs\superpowers\specs\2026-10-29-delivery-return-log-full.md` lines 312–313) says "Warehouse pieces are not imported into returns"; the concept reverses that without saying why.
Requirement: split the import into two separately decided steps. Step 1, store-side lines, reasons, Aryo refs and expiry dates: pure data, reversible by delete, recommended. Step 2, warehouse counts into stock: not recommended; if the owner insists, it runs only with the guard list in Key Decisions (dry run, deterministic ids, typed values only, skip fakturs with existing returns, `reconcile_inventory()` = 0 rows before and after, signed-in user, explicit disposition).

**B3. Unit ambiguity plus a silent "OK = remainder" prefill turns a unit mistype into stock inflation, and the dropped yellow check was the only place that error surfaced.** (design F2; comprehension B1, B2; codebase 2, 8; implementation F4)
The concept says "Osave counts in boxes"; the sheet's own excerpt contradicts it (2610448 NO10 in packs, 2610319 NO10 in boxes: same SKU, same customer, different unit). Phase 1's detail already labels every PO line "pak", including `OSVN10B` boxes (`DeliveryDetail.tsx` lines 199–207; `id.ts` line 185); the feed and dialog speak butir; Negeri stock is kg. The concept's catalog fact "N30B has eggs_per_pack = 150" is contradicted by the repo seed (30, `20260114195826_*.sql` line 39); `OSVN10B` / `OSVN10O` / `OSVKP6O` appear in no migration, only in test fixtures and the live `pack_skus` table. With the yellow check dropped and OK pre-filled, a wrong unit is a silent restock of 9,350 phantom eggs.
Requirement: a per-SKU unit word from the catalog (box / pak), not inferred from `boxMode`, used on the PO lines too; every quantity input shows its piece equivalent inline as it is typed ("7 box × 180 = 1.260 butir · terkirim 86 box"); the warehouse side shows the computed total the typist must see ("1.260 butir: 1.088 OK + 172 pecah") rather than a silent default; a plausibility block (returned pieces for the line > the line's sold pieces cannot be saved); a non-blocking mismatch hint stays on the line when the returns' pieces differ from quantity × pieces per unit (a line hint, not a list flag or badge). The brief must cite the live `pack_skus` row (code, eggs_per_pack, base_pack_code, box_mode) for every SKU that appears in October's sheet; if N30B really is 150 while N30O is 30, say so, because an Osave "N30" on the wrong variant is a 5× error.

**B4. Three statements in the concept contradict the code or the sheet and must not be inherited by the design doc.** (codebase 1, 2, 4; implementation F6; structural F6; zoom-out F1)
(a) "The sheet's 22 columns": the sheet has 21 (`sheet_excerpts.md` line 9); the export emits 22 (`src\lib\deliveryExport.ts` lines 23–46) with "Butir Retak" inserted at column 18 and 8 headers that differ ("SKU" vs "Item", "Alasan" vs "Alasan Retur", "Keterangan Kondisi" vs "Catatan Kondisi", "Tgl Kembali Gudang" vs "Tgl Barang Balik", "Expired" vs "Tgl Expired", "No. Klaim" vs "No. Retur ARYO", "Status Klaim" vs "Status Tagihan", "(Pak)" vs "(pack)"); pasting shifts every column after 18. Phase 1 left this open as Q8. (b) "N30B = 150": see B3. (c) "`delivery_line_id` ... so stock, the activity feed and the log agree": the feed keys returns by `(outflow_id, sku_code)` (`src\hooks\usePriorReturns.ts` lines 44–60; `GroupedActivityLog.tsx` lines 124–133); returns write no `activity_logs` row at all; the link would be written only by the new bundle, phones keep old bundles indefinitely (CLAUDE.md deploy model), the Activities dialog stays reachable, and the 136 existing rows can never be back-linked from the client (no update policy). So every return that does not come through the new form shows "awaiting warehouse" in the log while stock and feed already moved: the exact failure the hypothesis claims to remove. Agreement is a property of reading the same key, not of adding a second one.

### Major

**M1. The delivery detail has no outflow ids, and shared invoice numbers silently pick one PO.** (design F3; codebase 3; structural F2, F3; implementation F2)
`returns` key by `outflow_id`; the `purchase_orders` view strips `relatedEntryId` (`20261022010000_buyer_profiles.sql` line 34) and `DeliveryPo` carries no logs. Resolution today means scanning `activity_logs` by `metadata->>'invoiceRef'` (the pattern in `useDelivery.ts` lines 26–38, with no index on that expression) and `findRelatedEntryId` (`useVoidEntry.ts` lines 152–177). Three invoice numbers are shared by two POs; the detail shows `pos[0]` (`useDelivery.ts` lines 49–55) and a return would be capped and restocked against the wrong order; `correct_order` can fix a ref only within 60 minutes, so a duplicate found a day later is permanent.
Requirement: extend `purchase_orders` additively with the egg outflow ids per row (`jsonb_agg(product, relatedEntryId) filter (where category = 'egg')` from the inner select, which still sees it) so the page never walks activity logs by name; refuse the warehouse save when `duplicatePos > 0` or `poState !== "ok"`, with a message naming both POs; add a duplicate-ref warning at PO entry in `QuickOutflowBuilder` (the `useDuplicateOrderCheck` hook exists); new tables reference `deliveries.id`, never `invoice_ref_norm`; void the two test POs before launch.

**M2. One implementation of the return rules; the dialog cannot be prefilled as-is; the direct path must share its core.** (zoom-out F2; structural F2; codebase 19 and Q1; implementation F9; design alt B; comprehension alt note)
`RecordReturnDialog.tsx` has no initial-values prop, its reset effect wipes every row on open (lines 245–257), `setBucket` clamps each bucket to `max − other buckets` (286–307) so a prefilled OK leaves no room to type pecah, and it renders every PO line (169–201). But the load-bearing rules live only inside it: box-SKU egg resolution via base pack × `boxCapacityMap` (127–147, mirroring `resolveBoxLine` in `outflowCalculator.ts` 99–115), outflow resolution, the shared-egg combined cap (283–307), and the submit loop with a running native remainder (316–360) that exists because `piecesToNative` rounds to 2 dp and two lines on a kg egg can otherwise exceed the server cap by 0.01 (`RETURN_EXCEEDS_OUTFLOW`, eps 1e-9). The dialog has already had one regression in exactly this logic (box SKU cap resolving to 0). The full spec's `delivery_log` SQL view would add a third copy of the 15.5 constant.
Requirement: extract `skuMap` and the submit loop (plus error classification) from the dialog into a pure lib (`buildReturnLines` next to `returnsCap.ts`), have the dialog import it, and have the delivery line call the same function plus `callRecordReturn`. The UI may differ; the core may not. No `delivery_log` SQL view. The dialog stays for the rare three-way split; the line can offer "Bagi rinci…" that opens it.

**M3. Two write paths exist for the lifetime of any old bundle; define "warehouse entry exists" by the key both paths write.** (design F8; implementation F6; zoom-out F1; codebase 7)
Requirement: the log derives the warehouse side from returns on the PO's egg outflows matching the line's `sku_code`, exactly as the feed does (`usePriorReturns(ids).bySku[skuCode]`), so returns from the Activities card, from old bundles and the 136 existing rows count automatically. `delivery_line_id` is at most a refinement for the rare same-SKU, two-physical-reason case (one typo pair in October); it is not the agreement mechanism. Every line the delivery page emits carries `sku_code` = the PO line's code and `product` = the egg product resolved through the base pack, or the feed shows nothing and retakan raises `PARENT_TYPE_MISSING`. The warehouse section lists all returns on the PO's outflows and flags unlinked ones ("retur tanpa baris").

**M4. The two-visit flow is built for the minority case.** (comprehension M2, M1; design F4)
Faktur balik and barang balik both have a median of one day after delivery and sorting happens in front of admin, so most of the time admin holds the faktur and the sorted goods together and the sheet lets them type one row. The concept sequences two saves on two visits. On day 3 admin holds goods, not a faktur number, and the list shows nothing per line (`Deliveries.tsx` lines 242–298); the detail opens with two cards that are already done.
Requirement: one row per line (SKU · qty + unit · reason · pecah in butir · OK computed and shown · No. Retur OSV) with one explicit save; pecah may be blank; orange = physical reason and no return yet; no screen forces "store side first". List rows carry a summary ("2 item retur · gudang belum", "1 tanpa No. Retur"); a faktur with an open orange line opens on the return section with the Phase 1 cards collapsed; the desktop split keeps the list scroll position after a save; Tab order and Enter-opens-confirmation specified for desktop typing.

**M5. Reasons with no physical return, and what "Kurang" means for stock.** (comprehension M3; design F7; codebase 13; structural Q6)
Kurang rows carry Qty Retur > 0 (2610574 AMTG 123 packs; 2610556 AMTG 20); a remainder prefill would restock 492 eggs the store says it never got. "Masih ditanyakan" is unresolved, not final. "Cancel" duplicates the "Batal" delivery status. Kurang means fewer eggs were loaded than the PO deducted, and `correct_order` closes after one hour, so the deduction is wrong forever with no record; one lens argues a `restock` return with reason `kurang` is numerically exact and should be allowed.
Requirement: for `kurang`, `revisi_po`, `cancel`, `masih_ditanyakan` the warehouse side is disabled with "Tidak ada barang balik"; no orange; the set is one constant in `deliveryFlags.ts`; `masih_ditanyakan` keeps a neutral marker and a filter chip so it gets closed; the brief states in writing what Kurang means for stock (default: no automatic change, a stock hint on the line in the style of `stockHintDitolak`, and a monthly "selisih kurang" figure in the export). Whether a Kurang restock path is allowed later is left for the owner.

**M6. Flags and the badge: do not extend `open_delivery_items`.** (structural F5; zoom-out F4; design F10; implementation F12)
The view is driven from `purchase_orders` and polled by the Header on every page every 30 s (Phase 1 N7). Adding line flags means joining `delivery_lines` and `returns` into a jsonb regrouping and keeping flag logic in SQL and in `deliveryFlags.ts`. Red (18 Osave rows without a ref today) would keep the badge lit for weeks over a backlog only office admin acts on, at the list.
Requirement: orange and red live as list chips with counts, classified once in `deliveryFlags.ts` from `delivery_lines` fetched for the range (same shape as `fetchDeliveriesInRange`). The badge never counts red; whether it adds orange to "faktur belum balik" is an owner call; if the badge changes, it reads tables (`deliveries` left join `delivery_lines` left join `returns`), and `open_delivery_items` is replaced, not extended. Flags are computed from tables, not from `purchase_orders`, so a pre-loading row can be flagged later.

**M7. The export, and what admin needs to stop using the sheet.** (codebase 1; structural F6; comprehension M6; zoom-out F5)
Novi's daily check is the Klaim tab's three counters and its filtered table. Status Tagihan has never been filled, so counters 2 and 3 are "all Osave return rows" and "all Osave pecah"; the counter that carries work is counter 1, rows without a return number, which is exactly the red flag. A CSV of the main tab alone makes her rebuild the filter every time. Item codes will print as `OSVN10B` where the sheet says `N10`. The transition paragraph names nobody who pastes the CSV where.
Requirement: 21 columns with the sheet's header strings copied verbatim from row 2; "Butir Pecah" = retakan + writeoff, "Butir OK" = restock, "Butir Retak" dropped (the O/R/H split stays in the feed); one TypeScript definition marked in the file header as a transition artefact to delete when the sheet is retired; one row per line client-side via `itemToLogRow`. On the list: the red chip count and a "butir pecah OSV tanpa No. Retur" total (replaces Klaim counter 1); a Klaim filter chip whose rows export as the claim CSV (faktur, item, qty, reason, expiry, pecah, ref). Counters 2 and 3 stated as Phase 3. The transition paragraph names the person and the step, or says the sheet stops on launch day.

**M8. Four words for broken eggs mapped three different ways; "retak optional" cannot be paraphrased.** (comprehension B3; structural F12; zoom-out F8)
The app's bucket labels are OK / Retak / Hancur; the concept maps pecah → `retakan` and also says "retak optional"; the full spec maps Butir Pecah → `writeoff` (line 66); an Indonesian reader maps "pecah" to "Hancur".
Requirement: one input labelled "Pecah (butir)"; a disposition control with explanatory labels, default "Retakan: dijual lagi sebagai telur retak", alternative "Hancur: dibuang"; no third "retak" bucket; a vocabulary table in the design doc (inputs OK / Retak / Hancur → restock / retakan / writeoff; reasons are a separate list; sheet words only in export headers); the Klaim total counts the same sum.

**M9. Osave detection and the reference field.** (comprehension M5; codebase 20; structural F9; implementation alt D)
EggKeep's buyer is `OSAVE` with DCs; the full spec's red rule `buyer matches OSV%` never matches it. FamilyMart carries a ref too (FMI-2610005). The field is called four things. One ref spans every line of a faktur and sometimes two fakturs (OSV-2610055).
Requirement: a buyer-level flag ("Perlu No. Retur") on the buyer profile decides red, not the name; the field is visible and optional for every buyer; one label on screen and in the export, "No. Retur OSV"; entered once per faktur and copied to its lines with per-line override; stored as `delivery_lines.claim_ref text` plus a generated `claim_ref_norm` (upper, trim); no `return_claims` table until a billing status exists (Phase 3 backfill is one `insert ... select distinct`).

**M10. The `delivery_lines` shape: facts as columns, state derived, nothing stock-side stored.** (structural F4, F7, F14; codebase 10, 11, 14; implementation F3, F7, F8; zoom-out F9; design F4, F13)
`pack_skus.code` is editable and `checkSKUDependencies` only greps `outflows.invoice_supplier`, so a renamed code or a changed box capacity silently changes what an old line means; the UUID plan does not inventory SKU-code pointers. The line upsert and the RPC are separate transactions. `record_return` takes one `reason` / `buyer_name` / `return_date` per call.
Requirement: columns `id` (client-generated, upsert on it), `delivery_id` (FK), `sku_code` (snapshot, never an FK), `pieces_per_unit` (snapshot at save), `quantity` (as typed, in the PO unit), `reason` (text with a client pick-list; no check constraint, under the old-bundle rule), `note`, `claim_ref` + `claim_ref_norm`, `expected_expiry`, `source` ('app' | 'sheet_import'), `import_key` (unique where not null), `created_by default auth.uid()`, `created_at`, `updated_at` trigger, optional `verified_by` / `verified_at` (Novi's tick). DB unique `(delivery_id, sku_code, coalesce(reason,''))`. RLS select / insert / update / delete for authenticated (a mistyped line must be deletable; precedent `20260820000001_stock_counts_delete_policy.sql`). No pieces, no warehouse dates, no status column: warehouse saved = returns exist; paraf gudang = `returns.user_id`; Tgl Barang Balik = min(`return_date`); OK / pecah = sums. Save order: line row first, then one `record_return` call per line per sorting event with the line's reason as the RPC reason, so a missing schema fails before stock moves and the orange flag is the recovery state. No `outflow_id` on lines, no NOT NULL PO-derived columns, no pre-seeding lines from `po.orderLines` (keeps the pre-loading door open). Add the new columns to `docs\uuid-migration\PLAN.md` with their class.

**M11. Error messages, concurrency and retries.** (comprehension M4; codebase 12; design F4, F6; zoom-out F2)
`callRecordReturn` returns raw Postgres text in native units ("RETURN_EXCEEDS_OUTFLOW: 70.19 returned + 11.61 > 81.29 sold") while admin typed pieces; a shared-egg failure names neither SKU. The dialog mints line ids at submit (line 350), so a retry after a timed-out success records twice within the cap. Two admins can both save the same line and both pass the cap. `useReturnOutbox` is mounted only on `Index.tsx` line 66; `/deliveries` mounts nothing, so an enqueued return would sit in localStorage until someone opens Activities on that device.
Requirement: `/deliveries` is online-only; on failure it keeps the typed values on screen and never enqueues ("Tidak ada koneksi, coba lagi"). Map `RETURN_EXCEEDS_OUTFLOW`, `RESTOCK_EXCEEDS_DEDUCTED`, `RESTOCK_UNALLOCATED`, `OUTFLOW_VOIDED`, `PARENT_TYPE_MISSING` to both locales in pieces per SKU with the remaining cap, the way `correctionErrorCode` does (`orderCorrection.ts` lines 48–55). Show prior returns per SKU (`bySku`) above the inputs before admin types; refuse a second save when returns already exist for the line, behind an explicit "tambah retur kedua". Generate return line ids once per form attempt and keep them until success. Add a read-only "Riwayat retur" list per faktur straight from `returns` (date, user, disposition, native qty + pieces).

**M12. Retakan inflow provenance.** (codebase 6)
`record_return` inserts the retakan child inflow with `gen_random_uuid()` and no link back (`20261008000000` lines 119–122); the recon view guesses by timestamp and quantity. "Why is NEGERI BIASA (RETAKAN) 400 kg over" is answerable only by date + quantity + user. Requirement: if the RPC is touched at all (for `void_return` or `delivery_line_id`), the same `create or replace` adds `inflows.return_id uuid references returns(id)` and sets it in the retakan branch; `void_return` needs it anyway.

**M13. Expiry.** (zoom-out F6; structural F10; codebase Q7; implementation F13; comprehension N5, Q7; design Q7)
Nothing reads `expiry_rules`; the seed's seven SKU rows are in sheet spellings that match no code; the table has no unique key, so re-seeding duplicates rows (Phase 1 F8, still open). Tgl Expired is filled on 98 of 108 return rows and goes on the Osave claim, so the field matters; 59 of 108 return rows are Osave, where the answer is "+30" regardless. Prefix matching is rejected by four lenses ("N" hits N4, N6, N10, N15, N30; "N30" hits both the 150-egg and 30-egg SKUs; "AMTG" misses `BK4AMTG`).
Requirement: `expected_expiry` defaults to `delivery_date + shelf_days` from the four buyer-level (null-SKU) rows and the default row, shown in a plain `<input type="date">`; SKU-level rules resolve the line's SKU to its base pack code first (box → `base_pack_code`, the same step `skuMap` / `resolveBoxLine` do) then exact-match re-keyed seed rows (N15B, N15O, N30B, N30O, BK4AMTG, P25, KP6B, KP6O; "N4" must be checked live); the remap is delete-and-reinsert with a unique index on `(coalesce(buyer_keyword,''), coalesce(sku_code,''))`; "Osave default 30" is the seed's `(null, null, 30)` row, no hardcoded fallback; no rules editor in Phase 2.

### Nits

Keep one explicit `verified_by` / `verified_at` tick (Novi) or drop it; the brief says who may tick, that it locks nothing, and that the list shows no flag for unticked lines. (design F14; zoom-out F7; comprehension N4)
- **N2. Negeri cap.** The outflow's kg was derived from the catalog `eggs_per_unit`; returns convert at a flat 15.5 (`returnsCap.ts`). `src\types\inventory.ts` line 108 is 15.5 so they match today; confirm the live catalog value or state that a full return may be clamped and show the clamp. (design F9; codebase 9)

(design F12; structural F11; implementation F11; codebase 16)
- **N4. Reason picker.** Pecah, Ditolak, Tukar guling, Kurang cover 105 of 117 sheet rows; four chips plus "Lainnya…" beats an 11-item select on a 375 px phone. The sheet's "Pecah 19,kurang 2" becomes two lines. (comprehension N1; design F13)
- **N5. Tukar guling.** Record the return and a note; the replacement is a new PO. An optional "No. Faktur pengganti" field was proposed by one lens and rejected by four; not in Phase 2. (all lenses Q5)
- **N6. The reconciliation export shifts retroactively** if October returns are imported (`v_recon_ledger` dates by `return_date`); run any import before the 23–31 Oct counts are re-read and say so. (implementation F14)
- **N7. "No. Faktur required" and "Sushi Toku as a buyer order"** are cheap and unrelated to Phase 2's shipping; old bundles keep writing POs without a ref. Do not gate the merge on them. (zoom-out F12)
- **N8. The concept's own wording.** Four sentences do not connect for a new reader: "retak optional" vs "pecah → retakan"; "the user who saves is the paraf gudang"; "Expiry is computed ... and editable" with no stated reader; "transition period" vs "no continuing sync". Rewrite them in the design doc; add a sheet-code → SKU-code table (N10 / NO10 → OSVN10B / OSVN10O, KpO6 → OSVKP6O, N 30 → N30B / N30O, AMTG → BK4AMTG, …). (comprehension M8)

### Strongest counter-arguments to the hypothesis

1. **Agreement comes from reading the same key, not adding one.** The feed already reads `(outflow_id, sku_code)`. `delivery_line_id` is written only by the new bundle, so for every old phone, every Activities-dialog return and the 136 existing rows, the log and the feed disagree, which is the failure the hypothesis claims to remove. (implementation; design; zoom-out)
2. **The hypothesis couples a slow, revisable, paper-driven process to an irreversible, capped, FIFO-restoring write with no undo.** Reasons change, "masih ditanyakan" resolves later, units are typed inconsistently in the sheet itself, goods sometimes route via TST. The sheet tolerated corrections; `record_return` does not. Until a correction path exists, every admin typo is a stock event only the owner can reverse by SQL. The data supports "admin types paper numbers" more than "admin posts stock". (structural; design; codebase; comprehension)
3. **The forcing function that makes admin leave the sheet is deferred to Phase 3.** Phase 1 got one test row because it digitised columns nobody needed. Phase 2 digitises the rest, in a form slower than a sheet row for the majority same-day case, while the list Osave and Aryo actually consume (the Klaim tab) stays in the sheet. Meanwhile the literal root problem, "returns stopped reaching stock on 14 Oct", has a zero-code fix: the owner repeats his 13–14 Oct back-entry weekly through the existing dialog. If Phase 2 ships without the Klaim chip and totals, it is Phase 1 again with more columns. (zoom-out; comprehension)

## Goals vs. Non-Goals

* **In-Scope Goals:**
  * One row per PO line on the delivery detail: quantity in the line's own unit with the piece equivalent shown inline, reason, note, No. Retur OSV, expected expiry (defaulted, editable), pecah in butir, OK computed and shown; one explicit, confirmed save that records the stock return through `record_return`; both halves savable in one visit.
  * A lean `delivery_lines` table (facts only, state derived from `returns`), DB-unique per (delivery, SKU, reason), deletable, with source / import_key / created_by audit columns.
  * One shared implementation of return-line resolution (box → pieces → native, outflow id, caps, shared-egg rows, running remainder, error mapping) used by the Activities dialog and the delivery line.
  * `purchase_orders` extended additively with egg outflow ids; warehouse save refused on duplicate or missing PO.
  * Orange ("gudang belum") and red ("tanpa No. Retur", by buyer flag) as list chips with counts; a Klaim chip with the "butir pecah tanpa No. Retur" total; flags classified once in `deliveryFlags.ts` from tables.
  * Export in the sheet's 21 columns with verbatim headers, one row per line, marked as a transition artefact; the Klaim rows exportable as the claim CSV.
  * Error messages for every `record_return` code in both locales, in pieces per SKU; prior returns and "Riwayat retur" visible on the line before typing; `/deliveries` online-only.
  * Import of October's store-side lines, reasons, refs and expiry as data (reversible).
  * A rollout checklist with pre-flight, old-bundle check, verification queries and an ordered rollback.
  * Decision recorded for: the correction path for a wrong warehouse save; what Kurang means for stock.

* **Out-of-Scope Non-Goals:**
  * Importing October's warehouse counts into stock through `record_return` (not recommended; if the owner overrides, only under the guard list).
  * `delivery_line_id` as the mechanism of agreement; a `record_delivery_return` wrapper RPC; the `delivery_log` SQL view; extending `open_delivery_items`.
  * A `return_claims` table or billing status (Phase 3); Klaim counters 2 and 3.
  * A third "retak" bucket; a `status` column on lines; stored pieces or warehouse dates on lines; a "paraf gudang" column equal to the saver.
  * Offline queueing from `/deliveries`; an admin "Import dari sheet" button.
  * An expiry-rules editor; prefix matching of expiry rules.
  * A "No. Faktur pengganti" link for tukar guling; automatic stock correction for Kurang.
  * A "to pack" status or PO-intake UI (separate brainstorm; Phase 2 only avoids closing the door).
  * Pasteurized egg yolk as a catalog item; TST own-use rows, "bu linda" and cash sales in this log.

## Key Decisions & Staging for Next Steps

### Resolved in this brainstorm

1. The delivery detail is the entry point; admin types; `returns` written by `record_return` stay the single stock truth; `delivery_lines` store-side numbers never feed stock; returns never go through `correct_order`.
2. One row per line, both halves in one visit, one explicit confirmed save per line (never on blur) that shows "N box × M = P butir · pecah X · OK Y → masuk stok" with sold pieces and prior returns beside it; a plausibility block above the line's sold pieces; a line-level mismatch hint stays; the yellow list flag stays dropped.
3. Unit word per SKU from the catalog (box / pak), piece equivalent shown inline everywhere a quantity is typed; the warehouse side displays butir, never kg; the dashboard shows Negeri restocks in kg and that is expected.
4. "Warehouse entry exists" is derived from returns on the PO's egg outflows with matching `sku_code`, as the feed does; `delivery_line_id` is not required for Phase 2.
5. One shared lib for return-line resolution, extracted from `RecordReturnDialog`; the delivery line calls it plus `callRecordReturn` directly; `/deliveries` is online-only; ids are generated once per attempt; a second save on a line with existing returns needs an explicit "tambah retur kedua".
6. `purchase_orders` gains egg outflow ids additively; warehouse save refused when the faktur matches zero or two live POs; duplicate-ref warning at PO entry; test POs voided before launch.
7. `delivery_lines` columns and rules as in M10; DB unique per (delivery, SKU, reason); deletable; no status, pieces or dates stored; `sku_code` and `pieces_per_unit` are snapshots; `pack_skus.code` treated as immutable once used, or `checkSKUDependencies` counts `delivery_lines` and `returns`.
8. Vocabulary: input "Pecah (butir)"; disposition default Retakan (labelled "dijual lagi sebagai telur retak"), alternative Hancur; no retak bucket; export "Butir Pecah" = retakan + writeoff.
9. Reasons with no physical return (`kurang`, `revisi_po`, `cancel`, `masih_ditanyakan`): line exists, warehouse side disabled, no orange, one constant in `deliveryFlags.ts`; `masih_ditanyakan` gets a neutral marker and chip; Kurang gets a stock hint; no automatic stock change.
10. Red flag by a buyer-level "Perlu No. Retur" flag, not by name; the field is optional for every buyer, labelled "No. Retur OSV", entered once per faktur and copied to lines; stored as `claim_ref` + `claim_ref_norm`; no `return_claims` until Phase 3.
11. Flags as list chips with counts and row summaries, classified once in `deliveryFlags.ts` from tables; the badge never counts red; `open_delivery_items` is replaced, not extended, if the badge changes at all.
12. Export: 21 columns, verbatim sheet headers, one row per line, client-side only, marked transition; plus the Klaim chip, its totals and the claim CSV. The design doc names who exports and pastes, or states that the sheet stops on launch day.
13. Error codes mapped to both locales in pieces per SKU; prior returns and "Riwayat retur" shown on the line; "PO dibatalkan" and "tidak cocok dengan PO" banners reused.
14. Expiry: buyer-level default + editable date; SKU rules via base pack code then exact match on re-keyed rows; delete-and-reinsert seed with a unique index; Osave default is data.
15. Import: store-side rows, reasons, refs and expiry only, as a script run once by the owner with a dry-run report, `source = 'sheet_import'`, `import_key` upsert, unmatched and shared fakturs listed for admin. Warehouse counts for 15–31 Oct are re-entered through the new UI, or stock is corrected by one manual inflow per product after the next physical count.
16. Pre-loading delivery record: new tables reference `deliveries.id` only; no NOT NULL PO-derived columns; no `outflow_id` on lines; no new status; no pre-seeding from `po.orderLines`; the warehouse save is the only step that requires a live PO.
17. `correct_order` stays blocked by returns (already true); `void_outflow` unchanged; voided POs keep their returns as history with flags suppressed.
18. Paraf gudang is not a column equal to the saver; at most one `verified_by` / `verified_at` tick that locks nothing.
19. **`void_return(p_return_id uuid, p_reason text)` ships in Phase 2** (owner decision A, 2026-11-02). It reverses that return's `return_restocks` rows oldest-first under the same lock order as `void_outflow`, voids the retakan child inflow it created (found through the new `inflows.return_id`), marks the return voided (`voided_at`, `void_reason`, `voided_by`), is idempotent on a second call, refuses when the restored stock has since been consumed below the restock (`RESTOCK_CONSUMED`), and is admin-gated in the UI like `void_outflow`. The same `create or replace` of `record_return` adds `inflows.return_id` and may carry `delivery_line_id` at no extra risk. It is a stock-side RPC change: the `data-integrity-reviewer` agent reviews the migration before merge, and the feed shows a voided return as such (delivered = sold − non-voided returns).

### Answers to the seven open questions in the concept

1. **Direct call or dialog?** Direct, inline on the line, through the shared lib extracted from the dialog; the dialog remains for the rare three-way split. Online-only.
2. **Line key?** DB unique `(delivery_id, sku_code, coalesce(reason,''))`, client-generated id, upsert; no UI merge code. (Five lenses; the YAGNI lens preferred deletable duplicates and was outvoted because the unique is also the import's idempotency key.)
3. **Where the Aryo ref lives?** `delivery_lines.claim_ref text` + generated `claim_ref_norm`; no `return_claims` now. (Unanimous.)
4. **Import: script or button?** Script, once, owner-run, dry-run first, store-side data only. (Unanimous against the button; four lenses against importing warehouse counts at all.)
5. **Tukar guling?** Return + note; nothing else.
6. **Reasons with no physical return?** Line exists, warehouse side disabled, orange skipped, Kurang stock meaning stated in writing.
7. **Expiry remap?** Base pack code then exact match on re-keyed seed rows with a unique index; no prefix matching; no editor UI.
