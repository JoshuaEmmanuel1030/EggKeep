## 1. Verdict

The hypothesis is sound in one respect: `returns` (written only by `record_return`) must stay the single stock truth, and everything warehouse-side on the delivery line must be a projection of it. It is wrong in its framing of "one save". Store side (day 0, from the faktur) and warehouse side (day 0 to 2, from the sorting) are two different moments, so the "two writes, one save" atomicity problem mostly dissolves once the design stops promising a second write to `delivery_lines` after the RPC. The real architecture risks are elsewhere: (a) the `purchase_orders` view strips the outflow ids the warehouse save needs, so the detail must rescan `activity_logs`, and with three shared invoice numbers that scan returns two POs' outflows; (b) the one-time import writes ~21,000 restocked pieces three weeks late, overlaps the owner's 13–14 Oct back-entry, and there is no `void_return`, so a wrong import is an SQL-only rollback; (c) the sheet's own excerpt contradicts the "Osave counts in boxes" unit rule, and the dropped yellow check was the only place that error would surface; (d) the deliveries page mounts no return outbox, so "offline outbox in between" does not exist on that page; (e) `Kurang` rows leave a permanent stock overstatement that nothing in the concept addresses. Cost and load are not an issue at this volume; the dominant query cost remains the `purchase_orders` regroup on every Header poll, unchanged by Phase 2.

## 2. Findings

**F1 — Blocker — Data-flow integrity / irreversibility.** The import collides with existing returns and cannot be undone. The 136 `returns` rows (30 Sep–14 Oct) were back-entered from the same sheet; the import covers 12–31 Oct, so 12–14 Oct fakturs would be recorded twice. `record_return` only rejects when the cumulative sum exceeds the outflow (`C:\Users\Joshua\JS\EggKeep\.claude\worktrees\main-ro\supabase\migrations\20261008000000_returns_sku_code.sql` lines 72–76); a second identical 172-piece retakan on a 15,480-egg outflow passes and mints a second RETAKAN inflow (lines 119–122). There is no `void_return` RPC anywhere in `supabase\migrations` (full listing checked), and `returns` has no client write policy (`20260904000000_returns.sql` lines 38–40), so a bad import is fixed only by hand-written SQL against `returns`, `return_restocks` and `inflows.remaining_butir`. Requirement for the brief: the import runs through `record_return` with a user JWT (`auth.uid()` is mandatory, line 38); it skips any faktur whose outflows already have `returns` rows and lists them; it has a dry-run mode that prints per-product native deltas and cap rejections before any write; a documented rollback (SQL or a `void_return` RPC) exists before launch. Also skip the two production test POs.

**F2 — Major — Faulty assumption (unit).** "Osave counts in boxes" is contradicted by the concept's own excerpt: `C:\Users\Joshua\JS\EggKeep\egm-reviews\delivery-return-log-phase2\sheet_excerpts.md` line 26 (faktur 2610448, NO10, Qty Retur 55, OK 409 + pecah 141 = 550 = 55 × 10, packs) versus line 20 (2610319, NO10, 2 → 360 = 2 × 180, boxes). Same SKU, same customer, different unit. The concept then drops the yellow check "by construction" and pre-fills OK as the remainder, so a unit mistake becomes a silent restock of 9,350 phantom eggs (55 × 180 − 550). Requirement: the quantity input must display the resolved unit and the computed piece total before save ("55 dus × 180 = 9.900 butir"), and a non-blocking mismatch hint must remain on the line when `sum(returns pieces)` differs from `qty × eggs per unit` (not a list flag, not a badge).

**F3 — Major — Data-flow integrity (outflow resolution).** The warehouse save needs an `outflow_id` per egg product; the `purchase_orders` view removes it (`C:\Users\Joshua\JS\EggKeep\.claude\worktrees\main-ro\supabase\migrations\20261022010000_buyer_profiles.sql` line 34, `metadata - 'relatedEntryId'`) and exposes no log ids. The detail would have to rescan `activity_logs` by `metadata->>'invoiceRef'` (the pattern already used for voided rows in `C:\Users\Joshua\JS\EggKeep\.claude\worktrees\main-ro\src\hooks\useDelivery.ts` lines 26–38; no index exists on that expression). With a shared invoice number the scan returns both POs' outflows while the detail silently shows `pos[0]` (useDelivery.ts lines 49–55); a return would then be capped and restocked against the wrong order. Requirement: add an additive column to `purchase_orders` (per egg product: `relatedEntryId` aggregated from the inner select, which still sees it) so each view row carries its own outflow ids with zero extra queries; the warehouse save is disabled when `duplicatePos > 0` until the ref is fixed. If the view is not extended, add an expression index on `upper(btrim(metadata->>'invoiceRef'))` filtered to outflow rows.

**F4 — Major — Atomicity / idempotency.** No wrapper RPC. The store-side line is a plain insert that is correct on its own (it is the Peachtree revision record) and whose "no warehouse entry" state is exactly the orange flag. The only same-moment pair would be "stamp paraf/date on the line after `record_return`"; remove it by deriving Tgl Barang Balik as `min(return_date)` and paraf from the explicit tick (F14). What is not idempotent today: `RecordReturnDialog` mints line ids at submit (`C:\Users\Joshua\JS\EggKeep\.claude\worktrees\main-ro\src\components\RecordReturnDialog.tsx` line 350), so a user retry after a timed-out success records twice within the cap; only outbox replay is safe. Requirement: generate the `delivery_lines.id` client-side and upsert on it; generate return line ids once per form attempt and keep them until success.

**F5 — Major — Failure mode (offline).** `useReturnOutbox` is mounted only on `C:\Users\Joshua\JS\EggKeep\.claude\worktrees\main-ro\src\pages\Index.tsx` line 66; `/deliveries` mounts nothing (`src\pages\Deliveries.tsx` imports only `useOfflineSync` for the count). A direct call that enqueues on network failure would sit in localStorage until someone opens Activities on that device. Requirement: `/deliveries` stays online-only as Phase 1 decided: on network failure show the error, keep the store-side line, do not enqueue. If enqueueing is wanted, mount `useReturnOutbox` at App level, not per page.

**F6 — Major — Silent double restock (concurrency).** Dila and Yani both type. Two warehouse saves for the same line pass the cap when the PO sold more than twice the returned amount (7 of 86 boxes) and restock twice. Requirement: before calling `record_return`, re-read returns linked to the line/outflow and refuse when any exist, offering an explicit "tambah retur kedua"; the form shows existing linked returns above the inputs.

**F7 — Major — Permanent stock overstatement (`Kurang`, `Revisi PO`).** `Kurang` means fewer eggs were loaded than the PO deducted (sheet: 2610574 AMTG 123 packs; 2610556 AMTG 20). `correct_order` closes after one hour (`C:\Users\Joshua\JS\EggKeep\.claude\worktrees\main-ro\supabase\migrations\20261021020000_correct_order_guards.sql` lines 89–91), so by the time admin logs it nothing can fix the deduction; the concept's §5 Q6 proposes a line with no warehouse side, which freezes the error. A `restock` return with reason `kurang` is numerically exact (same batches, same quantity). Requirement: decide explicitly; recommended: `kurang` and `revisi_po` allow a warehouse-side restock, orange flag applies; `masih_ditanyakan` is the only reason with no warehouse side until the reason changes.

**F8 — Major — Two write paths diverge (old bundles).** Phones keep old PWA bundles indefinitely (`C:\Users\Joshua\JS\EggKeep\.claude\worktrees\main-ro\CLAUDE.md` deploy model) and the Activities dialog stays (`src\components\GroupedActivityLog.tsx` lines 422–432). Both write `returns` without `delivery_line_id`, so the orange flag stays lit after stock moved and the feed and the log disagree, the exact thing the hypothesis promises to fix. Requirement: define "warehouse entry exists" as returns on the PO's outflows matching the line's `sku_code`, with `delivery_line_id` as a refinement only, or drop the column (alternative A below).

**F9 — Nit (pre-existing, becomes common) — Negeri cap.** The outflow's kg was derived at order time from the catalog `eggs_per_unit` ("≈15.5" per CLAUDE.md); the return converts at a flat 15.5 (`C:\Users\Joshua\JS\EggKeep\.claude\worktrees\main-ro\src\lib\returnsCap.ts` lines 12–18). If the catalog value is not exactly 15.5, a full-line return (which "OK = remainder" makes routine) is clamped by the client (RecordReturnDialog.tsx line 347) or rejected by the server. Requirement: confirm the NEGERI catalog value equals 15.5, or state that full returns may be clamped and show the clamp.

**F10 — Nit — Flags and cost.** Put orange and red into `open_delivery_items` as `exists()` subqueries at delivery grain (indexes on `delivery_lines(delivery_id)` and the returns link); the list mirror in `deliveryFlags.ts` needs two chunked `.in()` queries (pattern in `useDeliveryStatuses`, `src\hooks\useDeliveries.ts` lines 158–163), about 200 lines per 14-day range. Do not build the SQL `delivery_log` view from the full spec: the export is already TypeScript over list items (`src\lib\deliveryExport.ts`), and a SQL copy of the 15.5 constant is a second source. Badge should count orange only; red (18 Osave rows without a ref today) would keep the badge lit for weeks and widen the range to the oldest row (zoom-out N7). Load otherwise negligible: ~15 lines and ~30 return rows a day; the Header poll's `purchase_orders` regroup every 30 s remains the dominant cost and is unchanged.

**F11 — Nit — "Delivery before loading".** Today creation refuses without a live PO (`src\hooks\useDelivery.ts` line 127), `open_delivery_items` is PO-driven, and `buildDeliveryItems` labels a PO-less row "tidak cocok dengan PO" (`src\lib\deliveryFlags.ts` lines 89–106). Phase 2 must: keep `delivery_lines.sku_code` free of any PO dependency (nullable ordered-qty snapshot), gate only the warehouse section on a live PO (no outflows, no return), and not bake `status = 'terkirim'` into the store-side line rules. The relabel and a `to_pack` status are the intake brainstorm's job.

**F12 — Nit — `correct_order` is covered; `void_outflow` is not.** The guard exists: outflow locked, then `HAS_RETURNS` (`correct_order_guards.sql` lines 97–102). `void_outflow` has no returns check (`20260904000000_returns.sql` lines 185–230); a voided PO with linked lines drops out of the PO-driven view, so a pending physical return goes dark. State it; show orphaned lines on the detail with the existing "PO dibatalkan" banner.

**F13 — Nit — RPC shape.** `record_return` takes `reason` and `buyer_name` once per call, not per line (`20261008000000_returns_sku_code.sql` lines 30–32, 83). One call per delivery line is right; the import is one call per (faktur, reason). Reason on the line and on the return must be the same fixed list; the sheet's "Pecah 19,kurang 2" must be split or mapped to `pecah` plus a note.

**F14 — Nit — Paraf gudang carries no information.** "The user who saves is the paraf gudang" repeats Phase 1's mistake: admin always saves, so the column equals the PIC. Make paraf gudang the explicit "diperiksa" tick (Novi) stored on the line by that action, and derive the date from `min(return_date)`.

**F15 — Nit — Feed agreement needs exact keys.** The feed attributes per SKU by `bySku[skuCode]` on the egg's outflow (`src\hooks\usePriorReturns.ts` lines 57–60), and `record_return` resolves the retakan parent by `product` name (lines 89–99). The direct path must send `sku_code` equal to the PO line's `skuCode` and `product` equal to `pack_skus.egg_product` resolved through the base pack for box SKUs (RecordReturnDialog.tsx lines 127–147), or the feed shows nothing under the line and retakan raises `PARENT_TYPE_MISSING`.

## 3. Strongest counter-argument

Nobody used the return dialog not because of where it lives but because the stock return is a side effect admin does not care about; their job is the Peachtree revision and the Aryo bill. Phase 2 bets that hiding the stock write behind the paper entry gets stock right for free. But it couples a slow, revisable, paper-driven process (reasons change, "masih ditanyakan", units typed inconsistently in the sheet itself, goods sometimes routed via TST) to an irreversible, capped, FIFO-restoring write with no undo. Every admin typo becomes a stock event only SQL can fix, while the sheet tolerated corrections. Until a `void_return` or "koreksi retur" path exists, the honest version is: Phase 2 captures the store side and shows the warehouse side as a pending return confirmed with one tap, and stock writes stay behind an explicit, reviewable action.

## 4. Simpler alternatives

**A. No `delivery_line_id`, no `record_return` redefinition.** Link lines to returns by (PO outflows, `sku_code`), both already stored. Zero RPC migration, old bundles and the Activities dialog count automatically (fixes F8), no deploy-order risk. Gives up: per-line attribution when the same SKU appears twice with two reasons that both have a warehouse side (rare; the sheet's examples pair `pecah` with `kurang`), and FK integrity between the two tables.

**B. Store side only, warehouse side via the existing dialog prefilled** (full spec §5.2.4). One write path, cap UI, box-SKU resolution, outbox, all reused; the dialog needs three props (prefill pecah, lock to one SKU, deliveryLineId). Gives up "one form"; keeps a 560-line component with fragile effects as the only return UI. If the direct path is kept instead, extract the dialog's row-building and cap logic into a pure lib function used by both, so the cap/unit code exists once.

**C. Narrow the import.** Import store-side rows and Aryo refs for all 108 fakturs; import warehouse counts only for rows after the owner's back-entry (17–31 Oct), after a dry run. Gives up nothing of value: 12–16 Oct warehouse rows are already in `returns`.
