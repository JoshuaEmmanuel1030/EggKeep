## 1. Verdict

**Paraphrase (what I understand Phase 2 to be).** On `/deliveries`, each faktur's detail gains a per-SKU return table. Office admin (Dila or Yani) first types what the store sent back, read off the signed faktur: how many boxes or packs of each PO line, a reason from a fixed list, Osave's return number, a note. Later, when the warehouse sorts those goods in front of admin, admin types only the number of broken eggs; the app computes OK as "returned quantity in eggs minus broken" and immediately records a stock return through the existing `record_return` RPC (OK back into FIFO batches, broken into the RETAKAN child item), tagged with the line id, so stock, the Activities feed and this log show the same numbers. The list gets an orange marker (store side typed, warehouse not yet) and a red marker (Osave line with no return number); the yellow mismatch check goes away because the counts are derived. October's sheet rows are loaded once by script, and the CSV export imitates the sheet so Novi can keep checking as she does today. Billing status and PO intake are later work.

**Verdict.** The hypothesis is right about the place (the faktur detail, not the Activities feed) and the typist (admin). The shape as written is not safe to ship for the people who will use it, for three reasons. First, "type pecah, OK auto-fills, save = stock moves" puts an irreversible stock event one tap behind a prefilled number, and the repository has no way to undo a return (no `void_return`; `correct_order` refuses once a return exists). The sheet's own data shows the exact mistake that would inflate stock by ~9,000 eggs (faktur 2610448). Second, the unit story is confused in the current code and in the concept: the Phase 1 detail already labels Osave boxes "pak", the return dialog and feed speak butir, the catalog's 150-egg `N30B` is a pack SKU that admin calls a box, and Negeri is kg underneath. Third, the concept uses four words for broken eggs (pecah, retak, retakan, hancur) and maps them inconsistently with the app's existing labels and the export's two columns. Beyond these, the two-visit flow doubles navigation for the common case where faktur and goods come back on the same day, and the export does not actually match the sheet's layout, so Novi's checking habit does not survive it.

## 2. Findings

### Blockers

**B1. A prefilled OK plus an immediate stock call with no undo turns a unit mistype into stock inflation.**
Dimension: UX & ergonomics.
Friction: Admin types the store-side quantity on day 1 and pecah on day 2 or 3. If the day-1 number was in the wrong unit, the day-3 prefill is wrong by a factor of 10 to 18 and the cap will not catch it (the cap is the whole egg product sold on that outflow, not the line).
Evidence: sheet row 2610448 NO10 (`C:\Users\Joshua\JS\EggKeep\egm-reviews\delivery-return-log-phase2\sheet_excerpts.md` line 26): "55" returned, OK 409 + pecah 141 = 550, so the 55 was packs of 10, not boxes of 180. Under the proposed shape the prefill is 55 × 180 − 141 = 9,759 OK restocked instead of 409. Nothing in the repo reverses a return: no `void_return` anywhere (grep over the worktree returns nothing), and `C:\Users\Joshua\JS\EggKeep\.claude\worktrees\main-ro\supabase\migrations\20261021010000_correct_order.sql` line 83 refuses an order edit once a `returns` row exists. The Phase 1 detail saves text fields on blur (`C:\Users\Joshua\JS\EggKeep\.claude\worktrees\main-ro\src\components\deliveries\DeliveryDetail.tsx` lines 32-35, 281, 293); copying that pattern to the pecah field would fire a stock event on blur.
Requirement for the brief: (a) the warehouse save is an explicit button, never blur; (b) a confirmation step shows the arithmetic in words before the RPC: "7 box × 180 = 1.260 butir · Pecah 172 · OK 1.088 → masuk stok", with the line's sold pieces and prior returns next to it; (c) a plausibility block, not a hint: returned pieces for the line greater than the line's sold pieces (`packQty × eggsPerPack`, the same number `RecordReturnDialog` computes at `C:\Users\Joshua\JS\EggKeep\.claude\worktrees\main-ro\src\components\RecordReturnDialog.tsx` line 190) cannot be saved; (d) a reversal path (admin-only `void_return` that reverses `return_restocks` and voids the retakan inflow, or an equivalent) ships in Phase 2, because admin will make this mistake and today's only fix is the owner editing the database.

## 3. Strongest counter-argument to the hypothesis

The value Phase 2 is after is stock accuracy (~21,000 OK eggs since 17 Oct never re-entered stock). That value does not come from `delivery_lines`, store-side quantities, expiry or the import; it comes from admin recording a return per faktur, which the app has been able to do since September through `RecordReturnDialog`. Admin never used it because it is reachable only from the right order card in a feed, speaks butir and three buckets, and has no place for the reason list or the Osave number. The hypothesis answers that by building a second, two-stage return entry with its own table, view, flags, import and export, whose first stage (paper quantities that never touch stock) exists mainly to produce an orange flag for a wait that, by the sheet's own medians, usually does not happen. Meanwhile the same-day case, which is the majority, now takes two saves instead of one sheet row, and the second save is irreversible. If admin finds that slower than the sheet, they keep the sheet, which is exactly how Phase 1 ended (one test row in production).

## 4. Simpler alternatives

**A. One form, no delivery_lines.** Put a "Catat retur" section on the faktur detail that opens the existing return machinery for that PO's egg logs (the detail would need to fetch the PO's `activity_logs` rows, since `purchase_orders` carries no log ids and the dialog resolves outflows via `findRelatedEntryId`). Extend `returns` with `reason` (fixed list; the column already exists as free text) and `claim_ref`, and give the dialog a box/pak entry mode that converts to butir in front of the user. Store-side "Qty Retur" becomes derived (`ceil(pieces / eggs per unit)`), "Full" is derived, the orange flag disappears (there is nothing to wait for), red = Osave return row without `claim_ref`. Gives up: structured lines for Kurang / Revisi PO / Masih ditanyakan (they go in the delivery's notes or a tiny `deliveries.store_notes`), the ability to log the store side before goods arrive, and the sheet's exact 21-column export (it would be derived from `returns`, which is where the full spec said the warehouse columns come from anyway). Saves: `delivery_lines`, `delivery_log` view, the two-step UI, the store-side half of the import.

**B. Keep delivery_lines but make it one row.** If the store-side lines are wanted (for Kurang and for Phase 3 billing), keep the table but present each line as a single row: SKU · qty + unit · reason · pecah (butir) · OK (computed, shown) · No. Retur OSV, with one "Simpan" per line and the stock confirmation from B1 when pecah is filled. Orange = physical reason and pecah blank. Gives up nothing from the hypothesis except the enforced sequencing; it is the same data model with one save path.

Either way, extract `RecordReturnDialog.handleConfirm` (lines 316-389: cap clamp, pieces to native, one line per bucket, outbox classification) into a shared hook before building, so the delivery page does not reimplement the cap and the Activities path keeps working.

## 5. Recommendations on the section 5 open questions

1. **Direct RPC or prefilled dialog.** Direct, inline on the line, but through a shared submit hook lifted out of `RecordReturnDialog` (cap, shared-egg rows, pieces-to-native, error classification), not a second implementation. The dialog stays for the rare three-way split or loose-egg order; the line offers "Bagi rinci…" that opens it prefilled. Online-only for this page; do not route the delivery save through the return outbox (M4).

2. **Uniqueness of (delivery_id, sku_code, reason).** A DB unique constraint. The violation maps to one message ("Baris Pecah untuk N10 sudah ada, ubah baris itu"), and the UI's "+ alasan lain" on a SKU offers only reasons not yet used. UI-merge hides the double entry admin will make.

3. **Where the Osave number lives.** A text column on `delivery_lines` now, entered once per faktur and copied to its lines (N2). Create `return_claims` in Phase 3 by grouping distinct refs; nothing is lost. Do not create a one-column table now.

4. **Import.** A script run once by the owner with a dry-run report that admin reads first (which fakturs match, which are skipped as already returned, which rows have no PO). A button needs a CSV upload from a phone and will be pressed twice.

5. **Tukar guling.** Record the return and a note. Add one optional field "No. Faktur pengganti" so the swap's replacement PO can be found from the return; nothing else. The pecah from a swap is still billed to Aryo, so the Osave number applies.

6. **Kurang / Revisi PO / Masih ditanyakan.** The line exists (it is the store's claim and feeds the Peachtree revision); the warehouse side is disabled with "Tidak ada barang balik"; no orange. Masih ditanyakan is not final: keep a neutral marker and a chip. Kurang shows the stock hint (M3).

7. **Expiry remap.** Do not match by prefix ("N1" would hit everything; "N30" hits both the 150-egg and the 30-egg SKU, which have different shelf lives in reality). Either list the SKU codes explicitly in the rule rows (11 rules become about 20 rows, each with an EggKeep code admin can read in the editor), or defer the whole feature to Phase 3 and compute the date on export (N5). From the user's seat, the second is better: nobody in the app reads the date.
